# 设计与算法

前端为 Vite + TypeScript + Canvas，构建后由 Flask/Waitress 同源提供，默认仅绑定 127.0.0.1:5173。没有数据库、账户或订单服务。手绘和购物车保存在页面内存，刷新清空；只把深色模式选择写 localStorage。

后端模块：vision 处理 PNG 与真实 CLIP 推理；matching 做类别和名称关键词匹配；service 管理菜单、购物车、金额和报价；mcp_client 使用官方 SDK；optimizer 完成确定性搜索。Skill CLI 经同一 Flask API 入口复用这些模块。

## 视觉

使用 `openai/clip-vit-base-patch32`，六个食物文本提示加房屋、猫、乱线和白纸四个干扰提示，图文相似度 softmax 后输出六类中的 Top-3。分母包括干扰类，因此不是六类强制归一化。Top-1 分数低于 0.45、前两名差小于 0.12 或干扰类得分更高时提示不确定。阈值是开发启发式，未经数据集校准，不能解释为概率置信度。

首次推理自动下载权重到 `.cache/huggingface`，之后复用缓存与进程内模型。默认官方模型固定 revision `3d74acf9a28c67741b2f4f2ea7635f0aaf6f0268`，可通过 VISION_REVISION 更改。CLIP 权重约 605 MB；Windows 不支持 symlink 时可能占用更多磁盘。使用普通 Hugging Face 缓存和校验机制，没有自制镜像地址。模型加载/推理异常明确降级为手动类别，不输出硬编码结果。输入图片仅在本机处理，不调用外部图像识别 API。

作者绘制的六张简单线稿和一张干扰图见 examples/sketches，生成程序可重复运行。它们用于开发检查，不是独立随机测试集。README 中的结果只适用于这七张样本。

## 确定性餐单修复

把购物车展开为最多 6 个份数槽位，每个槽位只能选择原商品同类别商品。先过滤硬约束：锁定、忌口、热量所需信息完整；然后枚举笛卡尔积，按商品多重集合去重，过滤总热量上限，最后取得核价金额并过滤预算。

- 锁定：每一份原商品必须保留，优先级高于预算；冲突时无解。
- 忌口：明确包含对应 tag 的候选排除；Live 过敏原未知的商品也排除。Demo tag 均为合成数据，不能用于真实饮食判断。
- 热量：开启上限时任何营养缺失的候选都排除。
- 基本需求：每种类别的份数不变，不通过直接删光商品降低预算。

修改成本为原多重集合缺失的份数。偏好损失为 favorite_ids 商品缺失的份数。排序均为词典序：

| 策略 | 第一目标 | 第二目标 | 第三目标 |
|---|---|---|---|
| A | 修改份数最少 | 核价金额最低 | 商品 ID 的稳定顺序 |
| B | 核价金额最低 | 修改份数最少 | 商品 ID 的稳定顺序 |
| C | 偏好损失最少 | 修改份数最少 | 核价金额最低，再按 ID |

三种策略可能得到相同组合，这是合法结果。搜索穷举当前允许候选；不声称优化了未提供或无法报价的全体官方菜单。

Demo 核价是合成单价按整数分相加。Live 每个候选都调用 calculate-price，不能用大模型或单价总和假设优惠。仅在所有候选完成报价后选择方案；其中任意核价失败不返回伪最优结果。

## 报价生命周期

后端给出模式、门店和排序购物车的 SHA-256 摘要，以及创建时间和 120 秒有效期。前端购物车、模式、门店或约束编辑会清空报价与方案，并增加 revision；异步请求仅在 revision 相同时落地，避免旧返回覆盖新餐单。采用方案后要求重新核价。没有支付能力，报价不是订单承诺。

## 本地运行边界

服务没有多用户身份认证，设计用于单人本地运行。Token 是后端进程拥有者的凭据，所有使用此本地页面的人共享它；不要直接把当前服务暴露到公网。代码拒绝跨站 POST，限制上传大小、图像尺寸、购物车数量与只读工具名；这不等于完成生产级多租户部署。
